BUILD COMMANDS
npm run build is the complete production SSR build. npm run build:ssr remains an equivalent explicit command. npm run build:browser is the optional browser-only target and does not create a complete SSR deployment.
The .nvmrc pins the locally verified Node version (24.18.0); package.json lists the supported Node ranges. Use the matching Node toolchain and npm ci with development/build dependencies installed.

HOSTING
The reverse proxy must forward public pages AND /api/public/blogs and /api/public-cms-status to the frontend Node SSR process. Serve dist/upforex_Frontend/browser assets normally. Include dist/upforex_Frontend/server/data/public-blog-snapshot.json; build:ssr creates it automatically.
Do not upload just the browser directory to Apache: native initial SSR and the gateway require Node. Keep all existing HTTPS/hostname rules. Do not forward /api/public/blogs to the locked API backend.
For ng serve on port 4200, also run npm run serve:ssr on port 4000; proxy.conf.json forwards the public gateway to it. Use port 4000 to test production SSR/SEO.

CMS CACHE AND FRESHNESS
Only already-public English CMS articles are cached. The original stored IDs, copy and categories are retained. Existing reviewed copy corrections still run in WebBlogService.
The bundled source was fetched 2026-11-21T10:21:25.899Z: 61 articles. Initial body text has not been regenerated or invented.
A single background refresh uses the existing full public GET contract, at most once every five minutes on traffic, with an eight-second total deadline, bounded payload/count and one in-flight request per Node process. Failures retry at most once per minute. Cached requests do not wait for it.
Successful complete inventory replaces previous records, including deletions; a failed/partial inventory does not replace valid saved content. New/edited messages revoke native completion through the existing catalog checks until their translations are completed and verified.
Refresh persistence defaults to var/public-cms/snapshot.json. Give only the frontend process write access to var/public-cms, or set PUBLIC_CMS_CACHE_DIR to a persistent private directory. Never serve this directory statically. Source seed files need only read permission.
A valid public snapshot remains readable during a CMS outage. It is not automatically deleted at a fixed age: this avoids turning working indexed articles into errors solely because time elapsed. Missing or corrupt content returns 503 instead of an empty success page. There is no fabricated fresh timestamp.
GET /api/public-cms-status reports usable/stale/fetchedAt/reviewAfter/needsCmsAttention/lastError without secrets. It is no-store and returns 503 when no valid snapshot exists. stale:true means saved content is being served; do not call it fresh CMS verification. needsCmsAttention becomes true after seven days; monitor this and restore CMS service or refresh a reviewed public snapshot. Existing article changes/deletions/new publications are delayed while the upstream is unavailable.
